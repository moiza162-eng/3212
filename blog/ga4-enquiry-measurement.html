Analytics

Measure enquiries in GA4 without double counting

Choose a reliable success signal

A button click can show intent, but it can also happen when a required field is missing. For a lead form, choose a completion signal that fires after a successful submission. If the form lives on a separate provider's site and completion is unavailable, measure the outbound click and clearly label it as a proxy.

Walk through good and bad submissions

Use the site's test environment or an agreed test process. Trigger a validation error, submit successfully and refresh the confirmation page. Inspect the events in DebugView or your tag testing tool. The failure should record no completion and the successful journey should record one. Keep personal details such as names and email addresses out of analytics payloads.

Create a useful reporting view

Mark the confirmed lead event as a key event if it is an important business outcome. Compare completed enquiries with the form system's totals, allowing for consent choices and differences in counting. Document the event name, trigger and owner so the next site update can be tested against the same behaviour.

Define the enquiry in plain language

Write a sentence the marketing and web teams can agree on. For example, count an enquiry when the website confirms that a completed course interest form has been accepted. That definition excludes abandoned forms and unsuccessful attempts. Agree whether distinct successful submissions from the same person represent separate enquiries for reporting purposes. A duplicate technical trigger is different from a person legitimately submitting two forms. Keep the business definition beside the technical event name so a future developer can understand the intended behaviour. Document whether phone calls, embedded forms or external booking routes are covered by the same report or measured separately.

Attach the event to the actual success state

Work with the form owner to identify the reliable signal. A server response accepted by the website or an official provider callback can describe completion more accurately than a click listener on the submit button. If the form uses a confirmation page, consider what happens on reload, browser history and direct visits. Ensure two tags are not listening for the same success action. Include only information required for reporting, such as a generic form identifier or a course category. Keep free-text input and contact details in the form system. Review the instrumentation with the person responsible for consent behaviour before the change goes live.

Create a small test matrix

Test one successful submission on mobile and one on desktop. Try validation failure, a repeat press while the request is pending and a reload of the success state. If the network request fails and the form is reopened, check whether the retry creates only the intended completion. Where relevant, run the test with analytics permitted and with analytics disabled by consent, and confirm each path follows the site's configuration. Record the expected event count and the observed count for each case. Use dummy contact details in an approved test process and label or remove test enquiries in the destination system so the operations team can recognise them.

Reconcile the numbers after release

Compare a normal reporting period with totals from the enquiry system. Record the dates, time zone and which submission types are included. Consent decisions, tracking blockers and source differences can all affect the comparison. A sudden spike around a release deserves a closer look at tag changes and whether confirmation is counted more than once. A shortfall can also reveal a route that was never instrumented, such as an embedded form or a new campaign page. Assign someone to check this after major releases. Keep one documented example of a successful journey and the expected event output. That gives the next reviewer a concrete reference before they decide whether a difference represents a tracking problem or a difference in coverage.

Keep test traffic identifiable through an agreed testing process. If colleagues test on the live site, tell the team when it is happening and record the window in the change log. This gives analysts a way to explain unusual counts without discarding legitimate enquiries. Check the receiving system alongside analytics so a working event cannot hide an underlying failure to deliver the enquiry itself.
